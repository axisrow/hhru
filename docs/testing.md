# Тестирование

Каждый файл тестов имеет ровно один маркер категории:

- `unit` — чистая логика без сети;
- `integration` — связки модулей на моках и HTML-фикстурах;
- `smoke` — быстрая проверка сборки или CLI;
- `e2e` — сквозной путь на фикстурах без сети;
- `live_read` — чтение живого hh.ru;
- `live_write` — обратимая мутация своего аккаунта, незаметная посторонним
  (например, создать и удалить черновик резюме).
- `live_write_danger` — необратимая мутация или действие, видимое посторонним
  (публикация резюме на модерацию, отклик, bump, ответ в чате, отзыв отклика).

Граница для команд: `copy-resume` — `live_write`; `publish-resume`, `apply`,
`bump`, `run`, `reply-employers` и `clear-negotiations` — `live_write_danger`.

Обычный `pytest` безопасен по умолчанию: live-тесты исключены из сбора. Тесты
без `live_*` дополнительно получают защиту от случайного запуска браузера:
`tests/conftest.py` подменяет `compute_driver_executable` — узкое место
запуска процесса-драйвера Playwright, общее для sync API, async API и
прямого построения `PipeTransport`. Патч ставится в `pytest_configure`, то
есть ДО сбора тестов: код на уровне модуля исполняется уже на импорте, до
применения `-m` и до любой фикстуры, поэтому граница держится на процессе, а
не на имени функции/класса, которое можно импортировать под алиасом,
захватить в шапке модуля до старта фикстуры или обойти через
`importlib.reload`. Доступ к движку открывается только на время теста с
маркером `live_read`/`live_write`/`live_write_danger` (автоиспользуемая
фикстура `_allow_live_browser`) и не протекает на соседние тесты.

Перехват не зависит от того, как тест добрался до браузера: через
`browser.launch_context`, через локальный импорт внутри функции, через
ссылку или алиас фабрики, захваченные в шапке модуля, через `async_playwright`,
или в обход `launch_context` вовсе (`auth.login` вызывает `sync_playwright()`
напрямую).

Тесту, который мокает браузер сам (см. `test_browser_navigation`), защита не
мешает: его `monkeypatch` ложится поверх настоящего вызова, и исполняется
только его собственный мок — до границы процесса-драйвера дело не доходит.
Инвариант закреплён в `tests/test_live_browser_guard.py` — если появится
новый путь к движку, эти тесты должны его поймать.

Для чтения живого сайта запускайте явно `pytest -m live_read`. Безопасные
мутационные тесты запускайте через `./scripts/live_test_safe.sh`. Опасные
мутационные тесты запускаются только через шлюз `./scripts/live_test.sh`; каждый
его вызов требует отдельного подтверждения harness. Не добавляйте новые
live-тесты без явной необходимости и не запускайте их в CI.

## Как проверить канал ASK

Чтобы безопасно проверить, что запрос подтверждения ASK доходит до пользователя,
запустите:

```sh
./scripts/live_test.sh --dry-run
```

Ожидается ask-запрос. После разрешения скрипт выведет `[dry-run] канал ASK
работает; ничего не запускаю`, завершится с кодом 0 и не запустит pytest.
