# CLI-спецификация hhru_bot

> Эталон набора команд и формата вывода. На этот документ ссылаются feature-ишью,
> реализующие отдельные команды (`#21`). Это **спецификация**, а не реализация —
> код команд живёт в `src/hhru_bot/commands/*.py`, по одному модулю на команду,
> и авторегистрируется через `pkgutil.iter_modules` (0 правок `cli.py`).

## 1. Принципы интерфейса

- **Единственный интерфейс — CLI** в терминале. Никакого веб-дашборда, Telegram-бота,
  TUI, GUI. Пользователь запускает команду вручную и читает вывод в терминале.
- **Вывод — только текст и ASCII.** Чистые ASCII-таблицы с границами `+---+`,
  текстовые префиксы-события в квадратных скобках, поток текста для логов/писем.
- **Никаких эмодзи нигде.** Образцы `s3rgeym/hh-applicant-tool` и `fikstt2/hh-ai-agent`
  взяты как источник **семантики и набора команд**, а не формата: эмодзи-префиксы
  `s3rgeym` (иконки документа/глаза/конверта перед полями) и мессенджер `fikstt2`
  НЕ переносятся.
- **Ручной запуск, троттлинг и дневные лимиты не нарушаются.** Write-команды к hh.ru
  проходят через те же предохранители (`throttle.py`), что и `apply`/`bump`.
- **READ/WRITE-маркировка** у каждой команды (см. §3) — это контракт безопасности:
  `READ` ничего не меняет ни на hh.ru, ни локально; `WRITE-local` меняет только
  файлы пользователя; `WRITE-hh-ru` меняет состояние аккаунта на hh.ru и требует
  подтверждения или `--force`.

## 2. Формат вывода

### 2.1. ASCII-таблицы (табличные данные: `query`, `stats`, `funnel`, `list-resumes`, `settings`, `whoami`)

Границы через `+---+`, колонки через `|`, заголовок отделён. Повторно используемый
форматтер `report._ascii_table` — НЕ дублировать отрисовку в каждой команде.

```
+------------+--------+---------------------------+
| vacancy_id | status | reason                    |
+------------+--------+---------------------------+
| 12345678   | failed | кнопка отклика не найдена |
+------------+--------+---------------------------+
```

### 2.2. Текстовые префиксы-события

Уже используются в `apply.py`/`bump.py`/`search.py` — новые команды наследуют тот же
набор:

| Префикс     | Когда                                       | Пример                                    |
|-------------|---------------------------------------------|-------------------------------------------|
| `[OK]`      | действие выполнено успешно                  | `[OK] Резюме 'backend' поднято`           |
| `[FAIL]`    | действие не удалось                         | `[FAIL] 12345678 — кнопка отклика не найдена` |
| `[INFO]`    | информационная строка                       | `[INFO] Сессия действительна до 2026-08-01`|
| `[DRY-RUN]` | шаг в режиме сухого прогона                 | `[DRY-RUN] Отклик на 'Backend developer'` |
| `[skip]`    | вакансия отсеяна с причиной                 | `[skip] ... — в стоп-листе работодателей` |
| `[candidate]` | кандидат прошёл фильтр                    | `[candidate] score=+3.50 ...`             |

### 2.3. Экспорт (отчёты)

`--format csv` / `-o <file>` — чистый CSV без украшательств (для `> report.csv` или
трубки в `jq`/`sqlite3`). Реализовано в `query`/`stats`; новые отчётные команды
наследуют те же флаги.

#### `whoami` — кто авторизован + сводка аккаунта

- **Природа:** READ
- **Референс:** `s3rgeym whoami`/`id` (без эмодзи-строки).
- **Сигнатура:** `hhru_bot whoami [--resume <id>]`
  - Без `--resume` — сводка по аккаунту (резюме, недавние просмотры/приглашения
    из `responses` #12). Флаги `--config`/`--history`/`--headless` — общие.
- **Что делает:** проверяет действительность сессии (`storage_state_file`),
  показывает аккаунт и сводку. Не ходит на hh.ru за динамикой просмотров, если
  хватает локальной истории (`responses`/`actions`) — иначе один read-only обход
  `/applicant/negotiations`.
- **Вывод (ASCII-таблица):**
  ```
  $ hhru_bot whoami
  [INFO] Сессия действительна
  +-------------------+------------------------------+
  | Поле              | Значение                     |
  +-------------------+------------------------------+
  | Резюме            | backend, data-analyst        |
  | Откликов сегодня  | 12 / 40                      |
  | Новых ответов 24ч | 3                            |
  | Приглашений       | 1                            |
  +-------------------+------------------------------+
  ```
- **Заметка:** эмодзи-строка s3rgeym (иконка-идентификатор + счётчики резюме/просмотров/писем
  в квадратных скобках) заменяется на таблицу; «просмотры» берём из истории `responses`
  (account-scope), не из недокументированного счётчика hh.ru.

#### `list-resumes` — список резюме из конфига

- **Природа:** READ (локально из `config.yaml`; опц. read-only проверка статуса на hh.ru)
- **Референс:** `s3rgeym list-resumes`/`list`/`ls`.
- **Сигнатура:** `hhru_bot list-resumes [--status]`
  - `--status` — дополнительно сходить на hh.ru и показать, можно ли поднять
    (кулдаун `can_bump_now`) и дату последнего поднятия из истории.
- **Вывод (ASCII-таблица):**
  ```
  $ hhru_bot list-resumes --status
  +----------+----------------------------------+-----------+---------------------+
  | id       | resume_id                        | можно bump | последний bump      |
  +----------+----------------------------------+-----------+---------------------+
  | backend  | ABCDEF1234567890abcdef           | да        | 2026-07-27 10:05    |
  | analyst  | 0123456789abcdef0123             | нет (3ч)  | 2026-07-27 11:30    |
  +----------+----------------------------------+-----------+---------------------+
  ```
- **Заметка:** `resume_id` — числовой хвост `resume_url`; `id` — slug из конфига.

#### `config` — чтение/правка `config.yaml` из CLI

- **Природа:** READ (без аргументов / `-p` / `-e` / `-k`), WRITE-local (`-s` / `-u`)
- **Референс:** `s3rgeym config` (`-p`/`-e`/`-k`/`-s`/`-u`).
- **Сигнатура:**
  ```
  hhru_bot config                       # вывести содержимое config.yaml
  hhru_bot config -p                    # полный путь к config.yaml
  hhru_bot config -e                    # открыть в $EDITOR
  hhru_bot config -k <dotted.key>       # получить значение (напр. throttle.daily_apply_limit)
  hhru_bot config -s <key> <value>      # установить значение
  hhru_bot config -u <key>              # удалить ключ
  ```
- **Вывод:** текст (YAML-фрагмент для `-k`, путь для `-p`). Для `-s`/`-u` — `[OK]`.
- **Заметка:** правка пишется обратно в `config.yaml` через `yaml.safe_dump`,
  сохраняя структуру. Доступ к секретам (`storage_state_file`) через `-k` разрешён
  (файл всё равно в `.gitignore`), но `account.user_agent` и т.п. — обычные поля.
  ВАЖНО: `--config`/`--history` сами по себе глобальные флаги — команда `config`
  оперирует файлом, на который указывает `--config`.

#### `settings` — key-value настройки в `history.db`

- **Природа:** READ (без аргументов / `<key>`), WRITE-local (`<key> <value>`)
- **Референс:** `s3rgeym settings`.
- **Сигнатура:**
  ```
  hhru_bot settings                     # все настройки (ASCII-таблица)
  hhru_bot settings <key>               # получить значение
  hhru_bot settings <key> <value>       # установить значение
  ```
- **Вывод (ASCII-таблица):**
  ```
  $ hhru_bot settings
  +------+-------------------+----------------------------------+
  | Тип  | Ключ              | Значение                         |
  +------+-------------------+----------------------------------+
  | str  | user.email        | dmitry.kozlov@yandex.ru          |
  | bool | disable_version   | true                             |
  +------+-------------------+----------------------------------+
  ```
- **Заметка:** требует новой таблицы в `SCHEMA` (`settings(key TEXT PRIMARY KEY,
  value TEXT)`), дописывается в общий `SCHEMA`-блок `history.py` (НЕ migrations —
  см. CLAUDE.md и #50). Это единственная команда, которая пишет произвольные
  пользовательские настройки в БД (не action/response/offer).

#### `log` — хвост лога

- **Природа:** READ
- **Референс:** `s3rgeym log -f`.
- **Сигнатура:**
  ```
  hhru_bot log                          # последние N строк logs/hhru_bot.log
  hhru_bot log -f                       | follow (tail -f), прерывается по Ctrl-C
  hhru_bot log -n <count>               # количество строк (по умолчанию 50)
  ```
- **Вывод:** поток текста (`logs/hhru_bot.log`). Чувствительные ID (resume_id,
  сессия) в логе уже редacted уровнями логирования — команда ничего не фильтрует.
- **Заметка:** `follow` реализуется через чтение с polling (стандартный tail-loop),
  НЕ через фоновый демон. Прерывание по `KeyboardInterrupt` — exit 130 (как `main`).

#### `refresh-token` — проверить/обновить сессию

- **Природа:** READ (проверка) / WRITE-local (сохранение свежей сессии)
- **Референс:** `s3rgeym refresh-token`/`refresh`.
- **Сигнатура:** `hhru_bot refresh-token [--force]`
  - Без `--force` — только проверка: действительна ли сессия (`storage_state_file`).
  - `--force` — открыть headed-браузер и пересохранить сессию (как `login`, но без
    полного входа, если cookie ещё валидны).
- **Вывод:**
  ```
  $ hhru_bot refresh-token
  [INFO] Сессия действительна, обновление не требуется.

  $ hhru_bot refresh-token --force
  [OK] Сессия пересохранена в data/storage_state/hh_session.json
  ```
- **Заметка:** соответствие s3rgeym (сообщение «Токен не истек, обновление не требуется»
  с info-префиксом) — наш `[INFO] Сессия действительна ...`. У нас нет OAuth-токена, есть
  cookie-сессия Playwright, поэтому «обновление» = пересохранение `storage_state`.

#### `call-api` — произвольный read-only GET к hh.ru

- **Природа:** READ
- **Референс:** `s3rgeym call-api`/`api` (только read-only часть).
- **Сигнатура:**
  ```
  hhru_bot call-api [-m GET] <endpoint> [key=value ...]
  hhru_bot call-api /employers text="IT" only_with_vacancies=true | jq ...
  ```
- **Вывод:** сырой JSON (для трубы в `jq`). read-only `GET` только.
- **Заметка:** реализуется поверх той же Playwright-сессии (`storage_state_file`),
  что и остальные команды — НЕ заводит отдельный HTTP-клиент. Это аварийный люк для
  read-only эндпоинтов, которые не покрывают специальные команды; для рутинных задач
  предпочитать именованные команды.
- **Почему только GET (не POST/PUT/DELETE):** мутирующие методы hh.ru (отклик, отзыв,
  сообщение) требуют **OAuth Bearer access token** (официальная авторизация hh.ru API),
  которого у нас нет — мы работаем через cookie-сессию Playwright, а не OAuth. `s3rgeym`
  реализует `call-api` WRITE поверх собственного OAuth-клиента; заводить такой клиент
  в нашем проекте — отдельное крупное решение (за пределами этой спеки). Поэтому WRITE
  к hh.ru доступен **только через именованные команды** (`apply`/`bump`/`reply-employers`/
  `clear-negotiations`), которые проходят через браузерную форму/переговоры, а не через
  API. Запрещать POST/PUT/DELETE в `call-api` намеренно — иначе воркер упрётся в 401.

#### `reply-employers` — ответы в чатах с работодателями

- **Природа:** WRITE-hh-ru
- **Референс:** `s3rgeym reply-employers`/`reply` + семантика `fikstt2` (пересылка
  ответов HR — у нас как текстовый вывод + отправка своего ответа).
- **Сигнатура:**
  ```
  hhru_bot reply-employers [--dry-run] [--limit <n>] [--template <text>] --force
  ```
  - Без `--template` — использует `cover_letter_default` (аккаунт-wide шаблон; резюме-
    специфичный `cover_letter` неприменим, т.к. атрибуция к резюме недостоверна — см. ниже).
- **Scope — account-wide (без `--resume`):** команда НЕ принимает `--resume`. Страница
  `/applicant/negotiations` общая по аккаунту и не даёт достоверного признака, к какому
  резюме относится чат (то же ограничение, что у `responses` #12 — она тоже игнорирует
  `--resume`). `--resume` здесь был бы иллюзией границы действия: боевой запуск для
  `backend` мог бы ответить в чатах других резюме. Поэтому scope задаётся **явно**:
  account-wide по умолчанию + подтверждение/`--force`, без неявного сужения.
- **Что делает:** обходит чаты `/applicant/negotiations`, где **последнее сообщение от
  работодателя** (не от соискателя) и отвечает ещё не отправлен. Отправляет ответ.
  Тот же троттлинг, что у `apply`.
- **Вывод:**
  ```
  $ hhru_bot reply-employers --dry-run --limit 3
  === Ответы работодателям (account-wide) ===
  [DRY-RUN] -> 12345678 «Backend developer» @ Company
      Письмо:
      Здравствуйте! ...
  Итого отправлено: 0 (dry-run)
  ```
- **Idempotency / безопасность (fail-closed) — критично для этой команды:**
  - Текущая `responses`-схема (#12) хранит только последний статус `(vacancy_id, topic)`
    и **НЕ** хранит автора последнего сообщения, message-id, read-state и факт
    отправленного нами ответа. Поэтому дедупликация «ответили уже или нет» **не может**
    опираться на `responses`-историю — она недостаточна и приведёт к повторной отправке
    шаблона в диалог, где мы уже ответили.
  - Контракт: решать «нужен ли ответ» по **живой истории чата** (последнее сообщение
    от работодателя, read-state), читаемой с `/applicant/negotiations` в момент запуска —
    как делает `s3rgeym reply-employers`.
  - **Конкурентность (TOCTOU — обязательно):** последовательность «проверили чат →
    отправили ответ → записали результат» даёт гонку: два параллельных процесса (или
    ручной + плановый запуск) одновременно увидят последнее сообщение работодателя,
    оба отправят ответ, и лишь потом столкнутся на `UNIQUE(topic, inbound_message_id)`,
    который второе уже-отправленное внешнее сообщение НЕ отменит. Поэтому заявка на
    ответ должна создаваться **атомарно ДО отправки** как `pending`-claim по ключу
    `(topic, inbound_message_id)` (UNIQUE в отдельной таблице/схеме — расширение `responses`,
    часть feature-ишью). State machine: `pending` (claim взят) → `sent` (подтверждено hh.ru)
    / `failed` (ошибка отправки → claim снимается для повтора). Параллельный запуск видит
    `pending`/`sent` и fail-closed пропускает чат. Timeout/сбой оставляет `pending` —
    повторный запуск не отвечает повторно, пока claim не снят/не истёк.
  - Сериализация: работа по `topic` должна быть взаимоисключающей (один ответ на чат
    за раз); `--limit` ограничивает число чатов за запуск, а не параллелизм (он
    отсутствует — команда последовательна, как `apply`).
  - Без надёжного idempotency боевой режим небезопасен; воркер обязан реализовать
    fail-closed (лучше пропустить чат, чем ответить повторно/не туда).
- **Заметка:** отправка требует подтверждения (interactive prompt) либо `--force`
  (= «не спрашивать»). В боевой режим команда переходит только без `--dry-run`.

#### `clone-resume` — клонировать резюме

- **Природа:** WRITE-hh-ru
- **Референс:** `s3rgeym clone-resume`.
- **Сигнатура:** `hhru_bot clone-resume --resume <id> [--dry-run] --force`
  - Создаёт копию резюме на hh.ru (полезно, когда у резюме закончился лимит
    откликов). `--dry-run` показывает, какой POST уйдёт, без отправки.
  - `--force` **обязателен** для боевого режима — как и у всех WRITE-hh-ru команд.
    Без `--force` и без `--dry-run` → отказ с exit 1 (как `clear-negotiations`).
- **Вывод:**
  ```
  $ hhru_bot clone-resume --resume backend --dry-run
  [DRY-RUN] Клонирование резюме backend (resume_id ABCDEF...)
  [INFO] Ничего не отправлено.

  $ hhru_bot clone-resume --resume backend --force
  [OK] Резюме backend клонировано. Новый resume_id: ABCDEF...XYZ
  [INFO] Добавьте новое резюме в config.yaml, чтобы откликаться с него.
  ```
- **Заметка:** новое `resume_id` НЕ пишется автоматически в `config.yaml` — это
  ручной шаг пользователя (намеренно: клон нужно проверить на hh.ru). Каждое
  успешное клонирование пишется в `actions` (`action='clone_resume'`,
  `status='success'`) для аудита — тот же контракт, что у `clear-negotiations`.
- **Исключение из throttle (согласовано):** `clone-resume` — разовая операция
  (не поток откликов), поэтому `daily_apply_limit`/`bump`-кулдаун к ней не
  применяются. Но `--force`+аудит остаются обязательными (общий контракт WRITE-hh-ru:
  подтверждение + запись действия), и повторный клон того же резюме в короткий
  срок должен предупреждать (`[INFO] Уже клонировали X сегодня`), чтобы не плодить
  дубли на hh.ru. Дневной лимит на клонирование — на усмотрение feature-ишью.

---

#### `clear-skipped` — очистка записи о пропущенных вакансиях

- **Природа:** WRITE-local (история) — либо READ-рекомендация, см. заметку
- **Референс:** `s3rgeym clear-skipped --reason`.
- **Сигнатура:** `hhru_bot clear-skipped [--reason <reason>] [--dry-run]`
- **Проектное отличие от s3rgeym:** в нашей схеме пропущенные вакансии **НЕ
  хранятся в БД** — `filter_candidates` только логирует `[skip]` в момент
  `search`/`apply`. Поэтому прямой аналог невозможен. Варианты (выбирает
  feature-ишью):
  1. **READ-команда** — вывести из лога (или повторным `search`) сколько и по каким
     причинам было пропущено (повторяет фильтр, не меняя ничего).
  2. **WRITE-local** — если завести таблицу `skipped` в `SCHEMA` (отдельное
     решение), то чистит её с фильтром по `--reason` (`excluded_employer` /
     `excluded_keyword` / `already_applied` / `duplicate`).
- **Вывод (вариант 2):**
  ```
  $ hhru_bot clear-skipped --reason excluded_keyword --dry-run
  [INFO] Найдено пропущенных (excluded_keyword): 47
  [INFO] dry-run: ничего не удалено.

  $ hhru_bot clear-skipped --reason excluded_keyword
  [OK] Удалено 47 записей пропусков (excluded_keyword).
  ```
- **Заметка:** `--reason` берёт значения из причин `filter_candidates`. Если
  выбран вариант 1 (READ), команда переименовывается в `skipped` или становится
  флагом `search --skipped`. Это решение за feature-ишью, не за спекой.

#### `clear-negotiations` — отозвать отправленные отклики (ОПАСНАЯ)

- **Природа:** WRITE-hh-ru (деструктивная — отменяет реальные отклики на hh.ru)
- **Референс:** `s3rgeym clear-negotiations`.
- **Сигнатура:**
  ```
  hhru_bot clear-negotiations --vacancy <id> [--dry-run] --force
  hhru_bot clear-negotiations [--resume <id>] [--dry-run]      # только dry-run-план
  ```
  - `--force` **обязателен** для боевого режима. Без него — только `--dry-run`
    (показать, какие отклики будут отозваны) или отказ с exit 1.
- **Граница действия — критично (account-scope):** страница `/applicant/negotiations`
  общая по аккаунту и не даёт достоверной атрибуции отклика к конкретному резюме (то
  же ограничение, что у `responses` #12). Поэтому `--resume` **не является надёжной
  границей** деструктивного действия: отзыв «по резюме backend» может затронуть
  отклики других резюме. Контракт:
  - **Боевой режим (`--force`) разрешён ТОЛЬКО с явным `--vacancy <id>`** — точечный
    отзыв одной вакансии, где граница = конкретный отклик, а не недостоверная
    resume-атрибуция. Это безопасная форма по умолчанию.
  - **Пакетный отзыв по `--resume` в боевом режиме запрещён**, пока нет проверенного
    live-признака принадлежности каждой цели резюме. `--resume` без `--vacancy`
    работает **только как `--dry-run`-план** (показать кандидатов на отзыв) — даже с
    `--force` он падает с exit 1, требуя либо `--vacancy`, либо явного подтверждения
    account-wide批量-отзыва (отдельный флаг `--account-wide`, см. ниже).
  - При появлении надёжного live-признака атрибуции (будущее feature-ишью) каждый
    кандидат на отзыв проверяется на принадлежность; при **неизвестной или
    несовпадающей** атрибуции операция полностью прекращается (fail-closed), а не
    отзывает «на всякий случай».
  - Account-wide批量-отзыв (все отклики аккаунта) — отдельный явный флаг
    `--account-wide` + `--force`, без `--resume`/`--vacancy`; это экстремальная мера,
    требующая отдельного подтверждения. Спека не описывает его вывод подробно — на
    усмотрение feature-ишью, но с тем же аудитом.
- **Вывод:**
  ```
  $ hhru_bot clear-negotiations --vacancy 12345678 --dry-run
  [INFO] Будет отозван отклик: вакансия 12345678
  [INFO] dry-run: ничего не отозвано.

  $ hhru_bot clear-negotiations --vacancy 12345678 --force
  [WARN] WRITE-hh-ru: отзыв отклика на вакансию 12345678. Отменить нельзя.
  [OK] Отозвано: 12345678
  ```
- **Заметка:** самая опасная команда в наборе. Каждая успешная операция пишет в
  `actions` (`action='withdraw'`, `status='success'`) для аудита. Троттлинг
  применяется между отзывами (как в `apply`), чтобы не выглядеть как бот. `--force`
  без `--vacancy`/`--account-wide` → отказ; `--vacancy` без `--force` → только dry-run.

## 4. Семантика уведомлений (fikstt2 — как текстовый вывод)

Вместо push в мессенджер — тот же контент показывается в терминале при ручном
запуске. Это принцип `fikstt2/hh-ai-agent`, перенесённый с Telegram на stdout:

- **При `apply`** — текст отправленного сопроводительного письма. Уже есть в
  `--dry-run`; добавить в боевой режим при `--verbose`. → связано с #17 (AI-письма,
  CoverLetterProvider) и #52.
- **При `responses` (#12)** — новые ответы HR / приглашения / отказы с прошлого
  запуска, текстом + ASCII-таблица (`_print_responses_table` уже реализована).
- **Статистика** — счётчики откликов/ответов/приглашений за период (`stats` #11,
  `funnel` #13) — ASCII-таблицы, без эмодзи.
- **`reply-employers`** — текст отправляемого ответа (как письмо в `apply`).

## 5. Приоритеты и зависимости feature-ишью

READ-команды (быстрые, безопасные) → WRITE-local → WRITE-hh-ru → опасные. Каждая
команда = отдельное ишью, реализация не блокирует спеку.

| Приоритет | Команда             | Природа     | Зависимости                       |
|-----------|---------------------|-------------|-----------------------------------|
| 1 (READ)  | `whoami`            | READ        | `responses`/`actions` (есть)      |
| 1 (READ)  | `list-resumes`      | READ        | `config`, `throttle.can_bump_now` |
| 1 (READ)  | `log`               | READ        | `logging_setup` (есть)            |
| 1 (READ)  | `refresh-token`     | READ        | `auth`/`storage_state` (есть)     |
| 1 (READ)  | `call-api`          | READ        | Playwright-сессия (GET только)    |
| 2 (LOCAL) | `config`            | READ/WRITE-local | `config.py` (есть)           |
| 2 (LOCAL) | `settings`          | READ/WRITE-local | новая таблица в `SCHEMA`     |
| 2 (LOCAL) | `clear-skipped`     | WRITE-local | решение о таблице `skipped`       |
| 3 (HH-RU) | `reply-employers`   | WRITE-hh-ru | `responses` #12 + idempotency     |
| 3 (HH-RU) | `clone-resume`      | WRITE-hh-ru | селекторы страницы резюме         |
| 4 (ОПАСН) | `clear-negotiations`| WRITE-hh-ru | `responses` #12, `--force`+аудит  |

## 6. Критерии готовности feature-ишью (реализующих эту спеку)

- Команда зарегистрирована через `commands/<name>.py` + `register(subparsers)` —
  **0 правок `cli.py`** (авторегистрация через `pkgutil.iter_modules`).
- Вывод соответствует §2 (текст/ASCII-таблицы, без эмодзи; повторное использование
  `report._ascii_table`, НЕ дублирование отрисовки).
- Природа READ/WRITE соблюдена: WRITE-hh-ru команды проходят через `throttle.py`
  и требуют `--dry-run`/`--force`/подтверждения по §3.
- Тесты чистой логики (без браузера) на форматтеры и разбор аргументов — в `tests/`
  (конвенция characterization-тестов).
- `ruff check` + `ruff format --check` + `pytest` зелёные.
