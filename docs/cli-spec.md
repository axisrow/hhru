# CLI-спецификация hhru_bot

> Эталон набора команд и формата вывода. На этот документ ссылаются feature-ишью,
> реализующие отдельные команды (`#21`). Это **спецификация**, а не реализация —
> код команд живёт в `src/hhru_bot/commands/*.py`, по одному модулю на команду,
> и авторегистрируется через `pkgutil.iter_modules`. Браузерную команду также
> нужно внести в sandbox-preflight реестр `BROWSER_COMMANDS` в `cli.py` (#568).

## 1. Принципы интерфейса

- **Единственный интерфейс — CLI** в терминале. Никакого веб-дашборда, Telegram-бота,
  TUI, GUI. Пользователь запускает команду вручную и читает вывод в терминале.
- **Вывод — только текст и ASCII.** Чистые ASCII-таблицы с границами `+---+`,
  текстовые префиксы-события в квадратных скобках, поток текста для логов/писем.
- **Никаких эмодзи нигде.** Образцы `s3rgeym/hh-applicant-tool` и `fikstt2/hh-ai-agent`
  взяты как источник **семантики и набора команд**, а не формата: эмодзи-префиксы
  `s3rgeym` (иконки документа/глаза/конверта перед полями) и мессенджер `fikstt2`
  НЕ переносятся.
- **Ручной запуск, троттлинг и дневные лимиты не нарушаются.** Write-команды к hh.ru
  проходят через те же предохранители (`throttle.py`), что и `apply`/`bump`.
- **READ/WRITE-маркировка** у каждой команды (см. §3) — это контракт безопасности:
  `READ` ничего не меняет ни на hh.ru, ни локально; `WRITE-local` меняет только
  файлы пользователя; `WRITE-hh-ru` меняет состояние аккаунта на hh.ru.
- **Адресация резюме — slug ИЛИ реальный `resume_id` HH.ru (#319).** Аргумент
  `--resume` у команд адресации (`publish-resume`, `copy-resume`, `delete-resume`,
  `edit-*`, `about`, `resume-position`, `resume-sections`, `mark`, `stats`,
  `funnel`, `whoami`) принимает либо slug из `config.yaml`, либо числовой хэш
  `resume_id` (например, полученный из `list-resumes`). Хэш без записи в конфиге
  даёт «bare»-резюме без настроек: команды, работающие только с hh.ru
  (publish/delete/copy/edit-skills/edit-experience/mark/stats/funnel), выполняются
  без конфигурации; командам, которым нужна конкретная секция настроек
  (`ai_profile`, `education`, `resume_sections` — `about`, `resume-position`,
  `resume-sections`, `edit-education`), выдаётся точечная ошибка
  «требуется настройка …», а не «резюме не найдено в конфиге». Поисково-массовый
  путь (`apply`/`run`/`search`/`probe`) требует регистрации резюме в конфиге —
  отклик без настроек не имеет смысла.
- **`--force`/подтверждение — для новых деструктивных/массовых команд, не для всех
  WRITE-hh-ru.** Существующие `apply`/`bump`/`run` — **live-by-default**: они
  выполняют боевое действие при запуске, безопасность даётся opt-in `--dry-run`
  (показать план без действия) и предохранителями `throttle.py` (дневные лимиты,
  кулдаун 4ч). Это сознательное решение для CLI ручного запуска. **Три новые команды,
  чьё действие необратимо или массово** — `clear-negotiations`, `reply-employers`,
  `copy-resume` — используют **единый контракт подтверждения**:
  - **Боевой режим (без `--dry-run`) требует явного подтверждения** одним из двух
    равноценных способов: флаг `--force` ИЛИ интерактивный prompt (только если stdin =
    TTY; в неинтерактивном запуске/pipe — только `--force`, иначе отказ с exit 1).
    `--force` = «не спрашивать», prompt = то же подтверждение в диалоге.
  - Этот контракт одинаков для всех трёх команд — CLI-валидация единая. `--dry-run`
    работает без подтверждения (ничего не отправляет).
  - Глобального `--force` в `cli.py` нет; это per-команда флаг этих трёх команд.

### 1.1. Chromium и Codex sandbox (#568)

Codex на macOS не может запустить Playwright Chromium внутри ограниченного
`CODEX_SANDBOX=seatbelt`. CLI проверяет это сразу после разбора аргументов — до
разрешения путей, настройки логов, write-lock, `History` и `command_runs`.

| Режим | Требует Chromium |
|-------|------------------|
| `login`, `login-code`, `search`, `apply`, `bump`, `run`, `probe`, `responses`, `refresh-token`, `call-api`, `fill-form` | всегда |
| Создание, копирование, переименование, публикация, удаление и браузерное редактирование резюме | всегда |
| `clear-negotiations` | только `--account-wide` или боевой `--topic`; plan-only фильтры и `--topic --dry-run` — без браузера |
| `list-resumes` | да, кроме `--local` |
| `whoami` | только с `--online` |
| `stats`, `query`, `funnel`, `market`, `list-resumes --local`, обычный `whoami`, `import-cookies` | нет |

При sandbox-запуске браузерной команды CLI завершает работу с exit code `1` и
маркером `CODEX_SANDBOX_BROWSER_REQUIRED`, не начиная браузерное действие или
durable run. В Codex ту же команду надо с первого раза выполнять с
`sandbox_permissions=require_escalated`; `--headless` не отменяет это требование.
Elevated-разрешение относится только к запуску процесса и не заменяет `--dry-run`,
`--force` или явное пользовательское подтверждение внешнего WRITE-действия.

`CODEX_SANDBOX_NETWORK_DISABLED` не участвует в проверке: этот флаг может
оставаться установленным и на разрешённом elevated-пути. Существующий
`CODEX_SANDBOX_BROWSER_FAILURE` остаётся резервной диагностикой реального
Crashpad/Mach-port сбоя, если среда не была распознана preflight-проверкой.

## 2. Формат вывода

### 2.1. ASCII-таблицы (табличные данные: `query`, `stats`, `funnel`, `list-resumes`, `settings`, `whoami`)

Границы через `+---+`, колонки через `|`, заголовок отделён. Повторно используемый
форматтер `report._ascii_table` — НЕ дублировать отрисовку в каждой команде.

```
+------------+--------+---------------------------+
| vacancy_id | status | reason                    |
+------------+--------+---------------------------+
| 12345678   | failed | кнопка отклика не найдена |
+------------+--------+---------------------------+
```

### 2.2. Текстовые префиксы-события

Уже используются в `apply.py`/`bump.py`/`search.py` — новые команды наследуют тот же
набор:

| Префикс     | Когда                                       | Пример                                    |
|-------------|---------------------------------------------|-------------------------------------------|
| `[OK]`      | действие выполнено успешно                  | `[OK] Резюме 'backend' поднято`           |
| `[FAIL]`    | действие не удалось                         | `[FAIL] 12345678 — кнопка отклика не найдена` |
| `[INFO]`    | информационная строка                       | `[INFO] Сессия действительна до 2026-08-01`|
| `[DRY-RUN]` | шаг в режиме сухого прогона                 | `[DRY-RUN] Отклик на 'Backend developer'` |
| `[skip]`    | вакансия отсеяна с причиной                 | `[skip] ... — в стоп-листе работодателей` |
| `[candidate]` | кандидат прошёл фильтр                    | `[candidate] score=+3.50 ...`             |

### 2.3. Экспорт (отчёты)

`--format csv` / `-o <file>` — чистый CSV без украшательств (для `> report.csv` или
трубки в `jq`/`sqlite3`). Реализовано в `query`/`stats`; новые отчётные команды
наследуют те же флаги.

## 3. Карта команд

### 3.1. Уже реализовано (не проектировать заново)

| Команда     | Назначение                                   | Природа        | Формат вывода                  |
|-------------|----------------------------------------------|----------------|--------------------------------|
| `login`     | ручной вход, сохранение сессии               | WRITE-local    | `[INFO]` + текстовые подсказки |
| `login-code`| единый вход по одноразовому коду             | WRITE-local    | `[OK]`/ошибка                  |
| `import-cookies` | импорт куки hh.ru из Chrome в storage_state | WRITE-local | `[OK]`/`[FAIL]`/`[INFO]` |
| `refresh-token` | проверка/пересохранение сессии            | READ / WRITE-local (`--force`) | `[INFO]`/`[OK]`/`[FAIL]` |
| `search`    | поиск вакансий по фильтрам (без откликов)    | READ           | `[candidate]`/`[skip]`         |
| `apply`     | отклик с письмом                             | WRITE-hh-ru    | `[OK]`/`[FAIL]`/`[DRY-RUN]`    |
| `bump`      | поднятие резюме (кулдаун 4ч, дневной лимит)  | WRITE-hh-ru    | `[OK]`/`[FAIL]`                |
| `run`       | полный цикл `apply` + `bump`                 | WRITE-hh-ru    | наследует                      |
| `probe`     | дамп формы отклика без отправки (#8)         | READ           | `[OK]`/`[FAIL]`                |
| `fill-form` | заполнение внешней формы без отправки (#276) | WRITE-local    | `[DRY-RUN]`/`[FAIL]`          |
| `stats`     | сводка и экспорт истории (#11)               | READ           | ASCII-таблица / csv / md       |
| `query`     | read-only SELECT к `history.db` (#45)        | READ           | ASCII-таблица / csv            |
| `responses` | мониторинг ответов работодателей (#12)       | READ           | ASCII-таблица                  |
| `funnel`    | воронка откликов (#13)                       | READ           | ASCII-таблица / md             |
| `mark`      | ручная пометка оффера (#13)                  | WRITE-local    | `[OK]`                         |
| `profile`   | управление профилем аккаунта (#287)          | READ/WRITE-local | ASCII-таблица / `[OK]`        |
| `schedule`  | генератор конфига launchd/cron (#18)         | READ           | текст (plist/crontab)          |
| `competitors` | сбор обезличенных резюме конкурентов | READ hh.ru / WRITE-local | текст + `[WARN]` |

Для разового поиска без изменения `config.yaml` команда `search` принимает
опциональный `--text <TEXT>`. Сигнатура:
`hhru_bot search [--resume <id>] [--text <TEXT>] [--max-pages N]`.
При наличии `--resume` текст временно переопределяет `resume.search.text`;
без `--resume` создаётся временный поиск с остальными фильтрами по умолчанию.

`resume-position` выбирает поверхность редактирования по identity-bound состоянию
резюме, а не по факту редиректа. Если hh.ru сообщает
`nextIncompleteScreenId=professional_role`, команда явно открывает
`/profile/resume/professional_role?resume=<id>`, подтверждает точный `resume_id`
и использует wizard выбора профессии; обычный редактор позиции в этом состоянии
запрещён. Перед продолжением wizard команда через его подтверждённый clear-control
сбрасывает унаследованные profession IDs, затем выбирает согласованный `role_id`
в каталоге: иначе свежая копия может автоматически опубликоваться со старой
профессией исходного резюме. Завершение wizard может автоматически опубликовать
резюме, поэтому успех подтверждается повторным чтением серверного состояния,
точного `role_id`/label и карточки резюме.
Изменение видимости остаётся отдельным действием и `resume-position` его не
выполняет.

`competitors collect --text QUERY [--execution-mode foreground]
[--progress-verbosity {0,1}] [--items-per-page N]` по умолчанию запрашивает
`items_on_page=100` и без
`--max-pages` обходит всю видимую пагинацию. Явный `--max-pages N` —
safety-cap: при наличии следующей страницы запуск становится `limited` и печатает
`[WARN]`. Итог отдельно показывает заявленное hh.ru количество, доступные
страницы, просмотренные карточки и уникально сохранённые резюме; если выдача
скрывает остаток до регистрации работодателя, печатается отдельное предупреждение.
Первая порция DOM может содержать только 20 ссылок; parser ждёт дорисовки
запрошенной сотой карточки до короткого таймаута, чтобы не принимать ранний
промежуточный DOM за полный размер страницы.
`--items-per-page` принимает 1–100 и предназначен в том числе для коротких живых
smoke-прогонов на 20 карточках; production-дефолт 100 не меняется.
Финальная сводка и `[STOP]` содержат измеренное `время`; плагины экстраполируют
его с короткого smoke на запрошенный пользователем объём и сообщают оценку с
диапазоном ±25% до запуска длинной команды.
После чтения первой страницы команда печатает `[ESTIMATE]`: ожидаемый объём,
запрошенные и фактически полученные карточки на страницу, диапазон времени
одних только настроенных пауз троттлинга и пометку, что ETA будет уточнён по
фактической скорости. Последующие `[HEARTBEAT]` и `[PROGRESS]` содержат
наблюдаемый ETA. Команда остаётся foreground-процессом; плагины обязаны удерживать
terminal session и транслировать новые строки до exit code.
`foreground` и progress verbosity `1` являются значениями по умолчанию; background
не поддерживается. Для запуска через Claude Code/Codex плагины обязаны явно
передавать `--execution-mode foreground --progress-verbosity 1`; `[START]`
подтверждает выбранные значения в stdout. Глобальный `--quiet` совместим с прежними
вызовами и эквивалентен progress verbosity `0`: промежуточный поток скрывается, но
финальная сводка, `[STOP]`, ошибки и файловый лог сохраняются.
Checkpoint `--resume` привязан также к `items-per-page`: smoke на 20 никогда не
продолжается как production-запуск на 100 и наоборот.

### 3.3. Недостающие команды (спроектировать → отдельные feature-ишью)

Карточки ниже — спецификация для будущих воркеров. Каждая команда = отдельный модуль
`commands/<name>.py` + отдельное feature-ишью. Порядок карточек — по приоритету
(READ-команды раньше WRITE-hh-ru, опасные — последними с `--force`).

> **Граница эталона (#55).** Карточки фиксируют то, что стабильно между реализациями:
> имя и сигнатуру команды, природу READ/WRITE, формат вывода и safety-границы
> (scope, обязательность подтверждения, обязательность идемпотентности, fail-closed).
> **Как** эти гарантии достигаются — модель хранения, состояния отправки,
> reconciliation, конкретные условия отказа — принадлежит feature-ишью на команду,
> а не эталону. Спека описывает контракт перед пользователем, не устройство кода.

#### `whoami` — кто авторизован + сводка аккаунта

- **Природа:** READ; по умолчанию локальная проверка, `--online` — read-only проверка на hh.ru
- **Референс:** `s3rgeym whoami`/`id` (без эмодзи-строки).
- **Сигнатура:** `hhru_bot whoami [--resume <id>] [--online]`
  - Без `--resume` — сводка по аккаунту (резюме, недавние просмотры/приглашения
    из `responses` #12). Флаги `--config`/`--history`/`--headless` — общие.
- `--online` — после перехода на `/applicant/resumes` проверяет, что hh.ru
    принял cookie и не показал форму входа. Открывает браузер.
- **Что делает:** по умолчанию проверяет только наличие сохранённого auth-маркера в
  `storage_state_file`,
  показывает аккаунт и сводку. Не ходит на hh.ru за динамикой просмотров, если
  хватает локальной истории (`responses`/`actions`) — иначе один read-only обход
  `/applicant/negotiations`.
- **Вывод (ASCII-таблица):**
  ```
  $ hhru_bot whoami
  [INFO] Локальный auth-маркер найден; для проверки сессии на hh.ru используйте --online
  +-------------------+------------------------------+
  | Поле              | Значение                     |
  +-------------------+------------------------------+
  | Резюме            | backend, data-analyst        |
  | Откликов сегодня  | 12 / 40                      |
  | Новых ответов 24ч | 3                            |
  | Приглашений       | 1                            |
  +-------------------+------------------------------+
  ```
- **Заметка:** эмодзи-строка s3rgeym (иконка-идентификатор + счётчики резюме/просмотров/писем
  в квадратных скобках) заменяется на таблицу; «просмотры» берём из истории `responses`
  (account-scope), не из недокументированного счётчика hh.ru.

#### `list-resumes` — канонический список резюме аккаунта HH.ru

- **Природа:** READ (по умолчанию — read-only поход на hh.ru: goto + чтение
  DOM/SSR, ничего не кликается и не отправляется; `--local` — локально из
  `config.yaml` + локальной истории, hh.ru не дёргается)
- **Референс:** `s3rgeym list-resumes`/`list`/`ls`.
- **Сигнатура:** `hhru_bot list-resumes [--status] [--local]`
  - Дефолт (#320, ранее `--remote` #135/#315) — единая каноническая модель:
    открыть `/applicant/my_resumes` под сохранённой сессией и напечатать
    РЕАЛЬНЫЕ резюме аккаунта в одной таблице — `resume_id | alias | название |
    статус` (+ visibility и bump-колонки с `--status`). Черновики (status=not_finished) и
    опубликованные — в одном списке с явным статусом. `alias` — slug из конфига
    (запись-настройка есть) или «—» (remote-only: команды адресуются по
    `resume_id` без конфига — #319). Записи конфига без резюме на hh.ru
    (удалены) — `[WARN]`-сироты, не молчаливое исчезновение. Для remote-only
    резюме печатается YAML-фрагмент ОПЦИОНАЛЬНЫХ настроек.
  - `--status` — дополнительно показать, можно ли поднять (кулдаун
    `can_bump_now`), поисковую видимость и дату последнего поднятия. Видимость
    читается только из SSR-флага `isSearchable`; неизвестное значение
    показывается как «не подтверждена». Для опубликованного резюме с
    `isSearchable=False` печатается отдельное предупреждение. Bump-данные — из
    ЛОКАЛЬНОЙ истории, keyed by `resume_id` (работает для любых live-карточек).
  - `--local` — офлайн-просмотр overlay из конфига: таблица `id | resume_id`
    (+bump-колонки с `--status`), hh.ru не трогается.
  - **Сбой live-чтения — `[FAIL]` без fallback** (#320): невалидная сессия,
    отсутствующий/отозванный cookie `hhtoken`, форма входа, indeterminate
    (timeout/дрейф селектора) — каждое даёт явный `[FAIL]` с указанием
    выполнить `login` (или причиной), без трейсбека и БЕЗ молчаливой печати
    локального списка, который выглядел бы достоверным, но неполным.
- **Вывод (ASCII-таблица):**
  ```
  $ hhru_bot list-resumes --status
  ```

#### `call-api` — произвольный read-only GET к hh.ru

- **Природа:** READ
- **Референс:** `s3rgeym call-api`/`api` (только read-only часть).
- **Сигнатура:**
  ```
  hhru_bot call-api [-m GET] <endpoint> [key=value ...]
  hhru_bot call-api /employers text="IT" only_with_vacancies=true | jq ...
  ```
- **Вывод:** сырой JSON (для трубы в `jq`). read-only `GET` только.
- **Заметка:** реализуется поверх той же Playwright-сессии (`storage_state_file`),
  что и остальные команды — НЕ заводит отдельный HTTP-клиент. Это аварийный люк для
  read-only эндпоинтов, которые не покрывают специальные команды; для рутинных задач
  предпочитать именованные команды.
- **Почему только GET (не POST/PUT/DELETE):** мутирующие методы hh.ru (отклик, отзыв,
  сообщение) требуют **OAuth Bearer access token** (официальная авторизация hh.ru API),
  которого у нас нет — мы работаем через cookie-сессию Playwright, а не OAuth. `s3rgeym`
  реализует `call-api` WRITE поверх собственного OAuth-клиента; заводить такой клиент
  в нашем проекте — отдельное крупное решение (за пределами этой спеки). Поэтому WRITE
  к hh.ru доступен **только через именованные команды** (`apply`/`bump`/`reply-employers`/
  `clear-negotiations`), которые проходят через браузерную форму/переговоры, а не через
  API. Запрещать POST/PUT/DELETE в `call-api` намеренно — иначе воркер упрётся в 401.

#### `reply-employers` — ответы в чатах с работодателями

- **Природа:** WRITE-hh-ru
- **Референс:** `s3rgeym reply-employers`/`reply` + семантика `fikstt2` (пересылка
  ответов HR — у нас как текстовый вывод + отправка своего ответа).
- **Сигнатура:**
  ```
  hhru_bot reply-employers [--dry-run] [--limit <n>] [--template <text>] --force
  ```
  - Без `--template` — использует `cover_letter_default` (аккаунт-wide шаблон; см.
    оговорку о scope ниже).
- **Scope — account-wide (без `--resume`):** команда НЕ принимает `--resume`.
  > **Основание пересмотрено (#200, 2026-08-16).** Прежняя формулировка — «страница
  > `/applicant/negotiations` не даёт достоверного признака, к какому резюме относится
  > чат, поэтому `--resume` был бы иллюзией границы действия» — **фактически неверна**:
  > SSR `topicList[]` отдаёт `resumeId` (проверено на живой сессии, 7/7 переписок), и
  > `topic_refs()` его читает начиная с #200. Привязка достоверна.
  >
  > Запрет `--resume` у этой команды **сохранён**, но по другой причине: это
  > необратимая WRITE-операция в чужие чаты, и добавление сужающего флага требует
  > отдельного решения по семантике (что делать с чатами без `resumeId` при дрейфе
  > разметки — отвечать или пропускать; fail-closed или fail-open). Аналитику (#200)
  > это не блокирует: там цена ошибки — неверная цифра, а не отправленное сообщение.
  Пока scope задаётся **явно**: account-wide по умолчанию + подтверждение/`--force`,
  без неявного сужения.
- **Что делает:** обходит чаты `/applicant/negotiations`, где **последнее сообщение от
  работодателя** (не от соискателя) и отвечает ещё не отправлен. Отправляет ответ.
  Тот же троттлинг, что у `apply`.
- **Вывод:**
  ```
  $ hhru_bot reply-employers --dry-run --limit 3
  === Ответы работодателям (account-wide) ===
  [DRY-RUN] -> 12345678 «Backend developer» @ Company
      Письмо:
      Здравствуйте! ...
  Итого отправлено: 0 (dry-run)
  ```
- **Safety-контракт (эталонный уровень):**
  - **Источник истины — живая история чата,** а не локальная `responses` (#12): она
    хранит только последний бейдж `(vacancy_id, topic)` и не знает ни автора последнего
    сообщения, ни факта нашей отправки. Отвечаем там и только там, где последнее слово
    за работодателем.
  - **Идемпотентность обязательна:** боевой режим не должен отправлять повторный ответ
    в чат, где мы уже ответили.
  - **Fail-closed:** при любой неоднозначности (не удалось достоверно определить автора
    последнего сообщения или результат отправки) чат **пропускается** с `[FAIL]`, а не
    получает ответ «на всякий случай». Лучше пропустить чат, чем ответить повторно.
  - **Конкурентность тоже fail-closed:** сама команда последовательна (как `apply`), но
    это не защищает от одновременных запусков (параллельный/ручной поверх планового).
    Гарантия «повторный ответ не уходит» обязана держаться и в этом случае — при
    невозможности её обеспечить чат пропускается. `--limit` ограничивает число чатов
    за запуск, а не параллелизм.
  - *Механика идемпотентности (модель хранения, состояния отправки, reconciliation) —
    уровень реализации, а не эталона: см. решение по [#55](https://github.com/axisrow/hhru/issues/55)
    и feature-ишью на `reply-employers`.*
- **Заметка:** боевой режим (без `--dry-run`) требует подтверждения — `--force` или
  интерактивный prompt в TTY (единый контракт с `copy-resume`/`clear-negotiations`,
  см. §1). В неинтерактивном запуске без `--force` → отказ с exit 1.

#### `copy-resume` — скопировать резюме

- **Природа:** WRITE-hh-ru
- **Референс:** `s3rgeym clone-resume`. Имя команды переименовано под терминологию
  hh.ru: в интерфейсе действие называется «Копирование»/«Дублировать», не
  «клонирование» — команда должна находиться пользователем по слову из веба (#116).
- **Сигнатура:** `hhru_bot copy-resume --resume <id> [--title <должность>] [--dry-run] --force`
  - Создаёт копию резюме на hh.ru (полезно как заготовка нового профиля под
    другую специализацию, а не только при исчерпанном лимите откликов).
    `--dry-run` показывает план без отправки.
  - `--force` **обязателен** для боевого режима (или интерактивный prompt в TTY) —
    единый контракт подтверждения с `reply-employers` и `clear-negotiations` (см. §1).
    Без подтверждения и без `--dry-run` → отказ с exit 1.
- **Вывод:**
  ```
  $ hhru_bot copy-resume --resume backend --dry-run
  [DRY-RUN] Копирование резюме backend (resume_id ABCDEF...)
  [INFO] Ничего не отправлено.

  $ hhru_bot copy-resume --resume backend --force
  [OK] Резюме backend скопировано. Новый resume_id: ABCDEF...XYZ
  [INFO] Добавьте в config.yaml:
           - id: "<придумайте-id>"
             resume_url: "https://hh.ru/resume/ABCDEF...XYZ"
  ```
- **Заметка:** новое `resume_id` НЕ пишется автоматически в `config.yaml` — это
  ручной шаг пользователя (намеренно: копию нужно проверить на hh.ru). Вывод даёт
  готовый YAML-фрагмент для вставки. Опциональный `--title` после создания копии
  устанавливает ей желаемую должность через раздел `resume-position`; если копия
  создана, но title не установлен, команда сообщает `uncertain` и не считает запуск
  успешным. Каждое успешное копирование
  пишется в `actions` (`action='copy_resume'`, `status='success'`) для аудита —
  тот же контракт, что у `clear-negotiations`.
- **Восстановление после `uncertain` (#569):** повторный боевой запуск намеренно
  блокируется, пока в `actions` остаётся неподтверждённая попытка
  `copy_resume`. Сначала откройте список резюме на hh.ru и найдите новые черновики,
  созданные после исходной попытки; сравните их с источником и проверьте фактический
  title. Ненужный дубль удалите на hh.ru вручную (только после проверки его
  `resume_id`), а нужный черновик завершите/переименуйте вручную. Не обходите
  блокировку повторным `--force`: у такой попытки нет безопасного способа доказать,
  что новый клик не создаст ещё один дубль. Если список или identity черновика не
  удаётся подтвердить, оставьте запись `uncertain` и обратитесь к оператору.
  После ручного подтверждения фактического состояния на hh.ru блокировка снимается
  только ручной резолюцией в `history.db` (отдельной reconcile-команды намеренно
  нет): в `actions` вставляется `success`-строка с `created_at` позже существующей
  `uncertain` (тем же action-именем `copy_resume`, `reason` вида
  `manual reconciliation: confirmed via hh.ru UI`) — ложный `success` без
  подтверждения на hh.ru хуже блокировки, поэтому порядок «сначала сверка,
  потом вставка» обязателен. Для ручной SQL-резолюции сначала выберите конкретную
  строку `uncertain` и сверьте её `id`, `resume_id` и `vacancy_id`, затем в одной
  транзакции вставьте строку с теми же ключами — включая `vacancy_id` (для
  `copy_resume` это обычно исходный `resume_id`, а не пустая строка) — и timestamp
  в формате приложения с разделителем `T`, например:
  `strftime('%Y-%m-%dT%H:%M:%f', datetime(created_at, '+1 second'))` от
  выбранной строки. Не используйте `datetime('now')`: SQLite вернёт пробел вместо
  `T`, и текстовое сравнение в `has_unresolved_uncertain()` может не увидеть
  резолюцию как более позднюю. После вставки обязательно выполните эквивалентную
  проверку `has_unresolved_uncertain()` для того же `resume_id`/`copy_resume` и
  зафиксируйте транзакцию только если результат `0`; иначе откатите её и оставьте
  блокировку.
- **Исключение из throttle (согласовано):** `copy-resume` — разовая операция
  (не поток откликов), поэтому `daily_apply_limit`/`bump`-кулдаун к ней не
  применяются. Но `--force`+аудит остаются обязательными (общий контракт WRITE-hh-ru:
  подтверждение + запись действия), и повторное копирование того же резюме в
  короткий срок должно предупреждать (`[INFO] Уже копировали X сегодня`), чтобы не
  плодить дубли на hh.ru. Дневной лимит на копирование — на усмотрение feature-ишью.

- Один запуск создаёт одно резюме с одной основной профессией. Пункты каталога
  на следующем шаге — уточняющие специализации (до пяти), а не несколько
  независимых профессий в одном резюме. Для нескольких профессий запускайте
  команду отдельно для каждого резюме.
- Перед открытием визарда команда читает полный список существующих резюме и
  fail-closed отклоняет точное совпадение `--title`: второе резюме с той же
  должностью (например, второй «Маркетолог») не создаётся.
- После успешного создания печатается YAML-фрагмент с новым `resume_id` для ручной
  вставки в `config.yaml`; конфиг автоматически не изменяется.

#### `publish-resume` — опубликовать черновик резюме

- **Природа:** WRITE-hh-ru, опасная мутационная категория `live_write_danger` (требует ask)
- **Сигнатура:** `hhru_bot publish-resume --resume <id> [--dry-run] --force`
- Команда проверяет identity резюме, `status`, `canPublishOrUpdate` и наличие
  единственной кнопки «Опубликовать» в живом DOM. Без позитивного подтверждения
  этих условий она не кликает.
- Позитивный сигнал публикации — `isSearchable=True`: hh.ru отдаёт для уже
  опубликованных резюме разные значения `status` (`new`, `approved`,
  `modified`), поэтому один фиксированный статус не является надёжным.
- Если hh.ru сообщает `nextIncompleteScreenId` (например,
  `professional_role`), команда включает этот идентификатор в отказ и не
  пытается обходить незавершённый шаг через другой URL или кнопку.
- `--dry-run` только читает состояние и показывает намерение; `--force` обязателен
  для боевого клика. Изменение видимости — отдельное действие и этой командой не
  выполняется.

#### `profile` — единый профиль аккаунта

- **Природа:** READ (`show`) и WRITE-local (`set`/`unset`); браузер и hh.ru не используются.
- **Сигнатура:** `hhru_bot profile set "<текст вопроса>" "<значение>"`,
  `hhru_bot profile show`, `hhru_bot profile unset "<текст вопроса>"`.
- Профиль хранится в таблице `account_profile` в `history.db`. Поля с источником
  `manual` имеют приоритет над одноимёнными полями `hh_ru`. `unset` удаляет только
  ручную строку, поэтому автоматически считанное значение снова становится видимым.
- Поля `hh_ru` обновляются автоматически после успешного `login` или `login-code`:
  команда читает подтверждённые значения со страницы профиля аккаунта и не роняет
  вход, если необязательная страница недоступна. Это преднамеренно деструктивное
  обновление: если страница профиля подтверждена (найдена карточка с ФИО), но
  конкретное поле на ней отсутствует или пусто, ранее сохранённое значение этого
  поля с источником `hh_ru` удаляется — чтобы устаревший ответ не утёк в форму
  другого аккаунта при смене логина. Значения с источником `manual` (`profile set`)
  это не затрагивает.
- Ошибки React `#418`/`#423` на странице профиля считаются диагностикой, а не
  автоматическим отказом: после ограниченного recovery команда проверяет свой
  DOM-маркер. Если маркер или схема полей не подтверждены однозначно, старые
  данные сохраняются. Канонический разбор и критерии нового issue описаны в
  [`research/issue-567-profile-hydration.md`](research/issue-567-profile-hydration.md).
- `show` выводит все исходные строки (`question_key`, `value`, `source`, `updated_at`)
  ASCII-таблицей.
- Старые записи `resume.form_profile.answers` в YAML больше не читаются. Их нужно
  один раз перенести вручную командами `hhru_bot profile set "<вопрос>" "<значение>"`;
  автоматического переноса нет, чтобы не дублировать персональные данные в конфиге.

#### `questionnaire` — обучаемые шаблоны ответов на анкеты (#482)

- **Природа:** READ (`pending`, `templates`, `audit`) и WRITE-local (`set`, `unset`,
  `learn`); браузер не открывается, на hh.ru ничего не отправляется.
- **Сигнатуры:**
  ```
  hhru questionnaire pending   [--resume ID] [--limit N]
  hhru questionnaire templates [--resume ID]
  hhru questionnaire audit     [--resume ID] [--last N] [--template T] [--low-confidence]
  hhru questionnaire learn     [--resume ID] [--limit N]
  hhru questionnaire set TEMPLATE --mode static     --answer VALUE     [--resume ID] [--cluster C]
  hhru questionnaire set TEMPLATE --mode contextual --instruction TEXT [--example TEXT ...] [--resume ID] [--cluster C]
  hhru questionnaire unset TEMPLATE [--resume ID]
  ```
- **Шаблон** — семантический ключ, сводящий разные формулировки одного вопроса в одну
  запись (`salary`, `location`, `desired_role`, `business_segments`, `test_task`,
  `schedule`, `start_date`, `age`, `smoking` идут из коробки как seed-поля). Режим
  `static` отдаёт сохранённое значение как есть и LLM не вызывает;
  `contextual` хранит инструкцию и подтверждённые примеры, по которым ответ генерируется
  под конкретную вакансию.
- **Скоуп:** без `--resume` правится общий ответ аккаунта, с `--resume` —
  переопределение для этого резюме, которое имеет приоритет (тот же приём, что
  `manual` над `hh_ru` в `profile`). `unset` снимает только свой скоуп.
- **Очередь:** вопрос, на который бот не имеет права ответить сам, попадает в
  `questionnaire pending`, а вакансия пропускается с причиной `questionnaire_pending` —
  прогон продолжается. Очередь наполняется и в `apply --dry-run`, поэтому шаблоны можно
  обучить до первого боевого прогона. `learn`/`set` снимают эти skip-записи
  автоматически (вручную `clear-skipped` не нужен), но только для вакансий, у которых
  в очереди не осталось нерешённых вопросов: анкета с двумя неизвестными вопросами
  после одного ответа всё ещё непроходима, и возвращать её в поиск — впустую тратить
  запросы к hh.ru.
- **Комплаенс:** вопросы про документы, гражданство, разрешение на работу и судимость
  отвечаются ТОЛЬКО явным `static`-значением. Ни ключевые слова, ни LLM их не заполняют.
  Тема распознаётся по тексту вопроса, независимо от того, сопоставлен ли он с шаблоном.
  `set --cluster compliance --mode contextual` отвергается на входе.
- **Bootstrap:** `learn` добавляет в очередь вопросы из ранее собранных сканов
  (`probe --questionnaires-only`), поэтому обучать шаблоны можно на уже накопленных
  данных, не дожидаясь первого боевого `apply`. Повторяющиеся формулировки сводятся
  в одну строку очереди. `pending` такие вопросы только пересчитывает и НЕ записывает:
  она READ-команда, не берёт общий write-lock и должна оставаться доступной во время
  идущего `apply`.
- `learn` интерактивен: в неинтерактивном режиме печатает `[INFO]` и ничего не меняет;
  Ctrl-C печатает частичный итог и возвращает 130.
- **`audit`** (#488) — read-only снимок того, что уже записал живой `apply`
  (`questionnaire_questions` со `scan.source = 'apply'`; разведка
  `probe --questionnaires-only` идёт с `source='probe'` и сюда не попадает):
  ответ, источник, уверенность, сопоставленный шаблон/кластер. Нового LLM-вызова
  не делает — оценку правильности ставит человек или Claude Code, читая вывод.
  `--last N` — последние N ответов, `--template` — фильтр по шаблону.
  `--low-confidence` отбирает строки, на которые бот **не стал отвечать**
  (признак — пустой `answer`, который `apply/pipeline.py` пишет намеренно).
  Причина по строке не различима: так фиксируется и уверенность ниже порога, и
  отказ комплаенс-гейта, и «вопрос не сопоставлен ни с одним шаблоном» — сама
  причина лежит в `questionnaire_pending.reason` и видна через
  `questionnaire pending`. Фильтровать по самому порогу нечем: он живёт в
  `AnswerProposal.threshold` и в базу не пишется. Признаком `--low-confidence`
  по той же причине НЕ служит `filled`: он батчевый, пишется всему скану сразу,
  и уверенные соседи неуверенного вопроса тоже равны нулю.
  Из-за пустого `answer` аудит не показывает, «что бот хотел ответить, но не стал».
- **`audit` различает заполненное и незаполненное — но не доставленное.**
  Батчевость `filled`, мешающая ему быть признаком низкой уверенности, делает
  его верным признаком ДРУГОГО вопроса — заполнялась ли форма вообще: он тоже
  решается на весь скан. При единственном неуверенном вопросе
  `apply/pipeline.py` отсеивает вакансию целиком, и уверенный сосед с непустым
  `answer` в форму не попадает; такая строка печатается как
  `[форма не заполнялась]` и в счётчик заполненных не идёт. Отказ отвечать
  внутри заполненной формы — это `[без ответа]`; маркеры намеренно
  не однокоренные, иначе состояния сливались бы взглядом.
  **Граница точности:** `filled` фиксирует успешное ЗАПОЛНЕНИЕ формы, но не
  подтверждённую отправку (инвариант `history.py`), и пишется ДО анти-бот
  проверки, резервирования действия, письма и submit-клика. Поэтому заполненная
  форма может иметь отдельный исход отклика `success`, `uncertain` или `failed`.
  Колонка `исход` берётся из `actions` по `run_id + resume_id + vacancy_id` и не
  подменяет состояние формы. Если подходящей строки нет, печатается
  `[действия нет]`; для старой строки `actions` с `run_id IS NULL`, которую
  нельзя точно связать с прогоном, печатается `[исход неизвестен]`.
- **Вывод:** ASCII-таблицы через `report._ascii_table`, префиксы `[OK]`/`[INFO]`/`[FAIL]`.

#### `clear-skipped` — очистка записи о пропущенных вакансиях

- **Природа:** WRITE-local (история) — либо READ-рекомендация, см. заметку
- **Референс:** `s3rgeym clear-skipped --reason`.
- **Сигнатура:** `hhru_bot clear-skipped [--reason <reason>] [--dry-run]`
- **Проектное отличие от s3rgeym:** в нашей схеме пропущенные вакансии **НЕ
  хранятся в БД** — `filter_candidates` только логирует `[skip]` в момент
  `search`/`apply`. Поэтому прямой аналог невозможен. Варианты (выбирает
  feature-ишью):
  1. **READ-команда** — вывести из лога (или повторным `search`) сколько и по каким
     причинам было пропущено (повторяет фильтр, не меняя ничего).
  2. **WRITE-local** — если завести таблицу `skipped` в `SCHEMA` (отдельное
     решение), то чистит её с фильтром по `--reason`. Значения `--reason` должны
     соответствовать **фактическим reason-строкам `filter_candidates`**
     (`src/hhru_bot/search.py`): на сегодня это `"компания в стоп-списке"`
     (exclude_employers), `"стоп-слово в названии"` (exclude_keywords) и
     `"уже откликались ранее"` (history.has_applied). Спека предлагает enum
     `stoplist_employer` / `stoplist_keyword` / `already_applied` как стабильные
     ключи (feature-ишью маппит их на строки); `duplicate` отдельной причиной не
     существует — дедупликация идёт через `already_applied`.
- **Вывод (вариант 2):**
  ```
  $ hhru_bot clear-skipped --reason stoplist_keyword --dry-run
  [INFO] Найдено пропущенных (stoplist_keyword): 47
  [INFO] dry-run: ничего не удалено.

  $ hhru_bot clear-skipped --reason stoplist_keyword
  [OK] Удалено 47 записей пропусков (stoplist_keyword).
  ```
- **Заметка:** значения `--reason` — проектируемый enum для будущей таблицы `skipped`,
  привязанный к причинам `filter_candidates` (не к текущим reason-строкам напрямую —
  маппинг делает feature-ишью). Если выбран вариант 1 (READ), команда
  переименовывается в `skipped` или становится
  флагом `search --skipped`. Это решение за feature-ишью, не за спекой.

#### `clear-negotiations` — отозвать отправленные отклики (ОПАСНАЯ)

- **Природа:** WRITE-hh-ru (деструктивная — отменяет реальные отклики на hh.ru)
- **Референс:** `s3rgeym clear-negotiations`.
- **Сигнатура:**
  ```
  hhru_bot clear-negotiations --topic <id> [--dry-run] --force
  hhru_bot clear-negotiations --account-wide [--dry-run] --force
  hhru_bot clear-negotiations [--vacancy <id>] [--resume <id>] [--dry-run]   # только план
  ```
  - Боевой режим требует подтверждения по единому контракту §1: `--force` **или**
    интерактивный prompt в TTY. В неинтерактивном запуске без `--force` — отказ с
    exit 1; `--dry-run` (показать, какие отклики будут отозваны) работает без подтверждения.
- **Граница действия — критично (`--topic`, не `--vacancy`/`--resume`):** страница
  `/applicant/negotiations` общая по аккаунту, и **одна вакансия может дать несколько
  переписок** (разные `topic` — напр. отклик с разных резюме; см. `responses.py:153-156`
  и тест `test_upsert_same_vacancy_different_topics_are_distinct_rows`). Поэтому ни
  `--vacancy`, ни `--resume` не идентифицируют единственный отклик:
  - **Точечный боевой отзыв (`--force`) разрешён ТОЛЬКО с `--topic <id>`** — `topic`
    уникален для конкретной переписки (`/applicant/negotiations?topic=<id>`) и однозначно
    указывает один отзываемый отклик. Это единственная безопасная точечная граница.
    Единственная альтернатива боевому `--topic` — явный массовый `--account-wide` (ниже),
    который не притворяется точечным: он отзывает всё и требует отдельного подтверждения.
  - **`--vacancy` — только фильтр dry-run, НИКОГДА боевой флаг:** `--vacancy V --force`
    (без `--topic`) **запрещён всегда — exit 1 независимо от числа совпадений.**
    `--vacancy` допустим **только** как dry-run-фильтр (показать кандидатов и их topic).
    *Обоснование literal-запрета (число переписок по вакансии меняется во времени) —
    уровень реализации, см. [#55](https://github.com/axisrow/hhru/issues/55).*
  - **`--resume` в боевом режиме запрещён**; работает только как dry-run-план, даже
    с `--force`. *(Основание уточнено #200: привязка чата к резюме достоверна — SSR
    отдаёт `resumeId`. Запрет сохранён как safety-контракт необратимого массового
    отзыва, а не из-за недостоверности данных.)*
  - Account-wide массовый отзыв (все отклики аккаунта) — отдельный явный флаг
    `--account-wide` + `--force`, без `--topic`/`--vacancy`/`--resume`; экстремальная
    мера с отдельным подтверждением. Подробный вывод — на усмотрение feature-ишью,
    но с тем же аудитом в `actions`.
- **Вывод:**
  ```
  $ hhru_bot clear-negotiations --vacancy 12345678 --dry-run
  [INFO] Найдено переписок по вакансии 12345678: 1 (topic=77)
  [INFO] dry-run: ничего не отозвано.

  $ hhru_bot clear-negotiations --topic 77 --force
  [WARN] WRITE-hh-ru: отзыв отклика (topic=77, вакансия 12345678). Отменить нельзя.
  [OK] Отозвано: topic=77

  $ hhru_bot clear-negotiations --vacancy 12345678 --force
  [FAIL] Боевой отзыв требует --topic (--vacancy --force запрещён всегда). Запустите с --dry-run, чтобы увидеть topic.
  ```
- **Заметка:** самая опасная команда в наборе. Каждая успешная операция пишет в
  `actions` (`action='withdraw'`, `status='success'`) для аудита. Троттлинг
  применяется между отзывами (как в `apply`), чтобы не выглядеть как бот. Боевой режим
  (подтверждение по §1) разрешён **только** с `--topic` или `--account-wide`;
  `--vacancy`/`--resume` → только dry-run-план; `--vacancy --force` (без `--topic`) →
  всегда exit 1.

## 6. Критерии готовности feature-ишью (реализующих эту спеку)

- Команда зарегистрирована через `commands/<name>.py` + `register(subparsers)` —
  **0 правок `cli.py`** (авторегистрация через `pkgutil.iter_modules`).
- Вывод соответствует §2 (текст/ASCII-таблицы, без эмодзи; повторное использование
  `report._ascii_table`, НЕ дублирование отрисовки).
