# Issue #567: React hydration на страницах профиля

Дата проверки: 2026-08-24. Статус решения: задокументировано и покрыто тестами.

## Короткое решение

Ошибки React `#418` и `#423` в консоли hh.ru сами по себе не означают, что
страница профиля сломана. Они наблюдались на живой авторизованной сессии, после
чего клиентская перерисовка успешно создавала рабочий DOM.

Не открывайте новый issue только из-за этих сообщений в консоли. Результат
определяется по DOM-маркеру конкретной команды после ограниченного recovery в
`goto_hh()`, а не по чистоте консоли, `networkidle` или фиксированному `sleep`.

## Подтверждённые страницы и маркеры

| Путь | Маркер готовности | Дополнительный шлюз |
| --- | --- | --- |
| `/profile/me` (перенаправляет на `/applicant/profile/me`) | один видимый `h1[data-qa="title"]` с непустым именем | старая схема account-полей считается пригодной для очистки только при `count() == 1` у `[data-qa="profile-common-card-firstname"]` |
| `/applicant/profile/me`, секция языков | один видимый `[data-qa="profile-language-card"]` | авторизационная cookie, отсутствие login form, точный URL path и ровно одна карточка |

Login form входит в `ready_selector`: истёкшая сессия должна быть отвергнута
сразу, а не после ожидания всех попыток hydration recovery.

Селекторы отдельных имени, фамилии и города, подтверждённые 2026-08-18, уже
отсутствовали в live DOM 2026-08-24. Поэтому появление нового заголовка профиля
подтверждает восстановление страницы, но не разрешает трактовать отсутствие
старых полей как пустые значения. В этом состоянии автоматические `hh_ru`-данные
сохраняются без изменений. Это отдельный selector-drift, а не повтор #567.

## Контракт READ и WRITE

- React `#418`/`#423` допускаются, если после recovery появился конкретный
  маркер команды.
- Отсутствующий, скрытый или неоднозначный маркер — неопределённое состояние,
  а не пустой профиль.
- При неопределённом состоянии сохранённые profile-данные не очищаются и
  WRITE-кнопки не нажимаются.
- Planner и WRITE-путь языков используют один `_open_language_profile()`, чтобы
  одинаково проверять URL, авторизацию и единственность карточки.
- `acted=False` означает, что потенциально сохраняющий клик ещё не начинался.
  Непосредственно перед save-click выставляется `acted=True`, потому что ошибка
  Playwright после клика не доказывает, что запрос не ушёл.
- После save-click успех допустим только после повторного чтения сохранённого
  языка. Неоднозначный результат остаётся fail-closed/uncertain; WRITE не
  повторяется автоматически.
- `copy-resume` не менялся: его `ResumeProfileReadinessObserver`, один recovery
  reload и post-WRITE reconciliation уже реализуют более сильный контракт.

## Когда новый issue обоснован

Новый issue нужен только при наблюдаемом нарушении контракта, например:

- маркер не появляется после всех ограниченных попыток восстановления;
- маркер присутствует в количестве `0` или больше `1`, но команда всё равно
  очищает данные или начинает WRITE;
- команда нажимает save повторно после hydration/navigation error;
- после save-click заявляется успех без post-save подтверждения;
- подтверждённый live-маркер изменился или перестал быть однозначным.

Одного скриншота консоли с React `#418`/`#423` для нового issue недостаточно.
Нужны путь страницы, итоговый URL, количество и видимость рабочего маркера,
момент ошибки относительно первого save-click и результат post-save проверки.
