# hhru — CLI hh.ru-бота

Бот — CLI-инструмент на Playwright для поиска вакансий, откликов и поднятия
резюме на hh.ru. Запускается **только вручную** из терминала, каждая команда
логирует действия, поддерживает `--dry-run` и ограничена дневными лимитами +
случайными паузами (анти-фрод hh.ru). Не добавляй фоновые/скрытые режимы и не
обходи троттлинг/лимиты.

## Как вызывать CLI

Все команды запускаются через установленный CLI:

```bash
hhru <command> [flags]
```

Общие флаги: `--headless`, `--verbose`, `--config <path>`, `--history <path>`,
`--max-pages <n>`. `--resume <id>` опционален — без него команда идёт по всем
резюме из конфига.

## Главный принцип: CLI — конструктор примитивов

Команды CLI — это низкоуровневые примитивы для чтения и построчного изменения
полей резюме, вакансий и локальной истории, а не готовый end-to-end сценарий
для каждой формулировки пользовательской задачи. Не ищи отдельную команду под
каждый частный случай: нестандартную задачу нужно собрать из существующих
примитивов и выполнить поэтапно.

Например, «перевести резюме» означает:

1. прочитать и зафиксировать текущие значения нужных разделов;
2. сгенерировать перевод самостоятельно, без отдельной LLM-команды в CLI;
3. применить готовый текст по разделам существующими командами: например,
   `about --text`, `resume-position` с готовыми полями, `edit-skills --skill`,
   `edit-experience --entry`, `edit-education` с готовыми записями и
   `resume-sections` с готовыми записями;
4. перед каждым боевым сохранением запустить соответствующую команду с
   `--dry-run`, показать план пользователю и только после подтверждения
   сохранить изменения.

То же поэтапное комбинирование применяется к массовому обновлению раздела и
любой другой композиции. Не добавляй `translate-resume` или аналогичную
команду только потому, что пользователь сформулировал новую задачу.

## Правила безопасности (обязательно)

- **Write-команды к hh.ru — сначала `--dry-run`.** `apply`, `bump`, `run`,
  `publish-resume`, `reply-employers`, `clear-negotiations`, `copy-resume` меняют
  состояние аккаунта на hh.ru. Покажи план через `--dry-run` и спроси
  подтверждение перед боевым запуском.
- **Read-only для hh.ru.** `search`, `probe`, `stats`, `query`, `responses`,
  `funnel`, `whoami`, `list-resumes`, `market`, `log`, `schedule` ничего не меняют
  на hh.ru — запускай без подтверждения.
- **Уважай троттлинг и дневные лимиты.** Не запускай `apply`/`bump`/`run` чаще,
  чем позволяет бот (кулдаун поднятия 4 часа, дневные лимиты). Не обходи их.
- **Никаких эмодзи.** Вывод CLI — только текст и ASCII-таблицы. Не добавляй
  эмодзи в вывод и в свои сообщения о результате.
- **Не используй `page.request.*` и внутренние API hh.ru** — только команды бота.

## Первый запуск: создание аккаунта

Первичная настройка — пока файл `data/accounts/<имя>/config.yaml` не существует —
выполняется человеком вручную в терминале, а не агентом. Это этап ручной
настройки, а не работы бота: инструмент `hhru` (плагин) всегда подставляет
`--account <имя>`, а CLI резолвит пути аккаунта до выполнения команды
(`_resolve_paths` → `resolve_account_paths`), поэтому для несуществующего аккаунта
любая команда, включая сам `account create`, падает:

```
[FAIL] аккаунт 'default' не найден: data/accounts/default/config.yaml
```

### Штатная последовательность (выполняется человеком из корня проекта)

1. **Создать аккаунт** — `hhru account create default` (без `--account`).
   Создаёт `data/accounts/default/` из шаблона `config/config.example.yaml`.
   У команды нет `--dry-run`, поэтому через агента она не выполняется ни через
   инструмент (резолвер путей падает раньше), ни через bash (write-хук требует
   `--dry-run`) — только руками в терминале.
2. **Войти** — сразу после создания аккаунта предложи пользователю запустить
   `hhru login`. Откроется окно браузера (headed), учётные данные вводит человек.
   Сессия сохранится по пути `storage_state_file` из конфига — относительно файла
   конфига аккаунта, то есть `data/accounts/<имя>/storage_state/hh_session.json`.
   Не заставляй пользователя заполнять конфиг до входа — сессия нужна раньше.
3. **Заполнить конфиг** — `data/accounts/default/config.yaml`: вписать реальный
   `resume_url` вместо плейсхолдера `XXXXXXXXXXXXXXXXXXXXXXXX` (или
   `YYYYYYYYYYYY...` для второго резюме), настроить фильтры (`text`, `area`,
   `salary_from`, `exclude_keywords` и т.д.). После входа `resume_url` можно
   определить через `list-resumes` (см. шаг 4).
4. **Проверить** — `hhru whoami` (сессия, лимиты) и `hhru list-resumes`
   (реальное резюме привязано к конфигу).

### Создание аккаунта силами агента (автоматизированная среда)

Если аккаунт нужно создать через агента — вызови инструмент `hhru` с командой
`account`, флагами `--config data/config.yaml --history data/history.db create <имя>`
и `confirmed=true` — явные `--config`/`--history` отключают резолвер путей аккаунта,
и команда выполняется. Это обходной путь, а не штатная последовательность:
write-lock при этом ложится на `data/`.

**После создания аккаунта через агента — сразу предлагай `login`**, а не заполнение
конфига. Пользователь должен войти в hh.ru как можно раньше, чтобы сессия была
готова к следующим шагам. Конфиг заполняется после (или параллельно с) входом.

## Проверка готовности

Перед боевыми командами убедись, что бот настроен:

1. **Аккаунт** — `data/accounts/<имя>/config.yaml` существует (создаётся
   `account create`, см. «Первый запуск»). Если нет — это этап ручной настройки,
   не запускай боевые команды.
2. **Сессия** — `hhru whoami`. Если сессия
   невалидна — `login` (интерактивный вход, требует пользователя).
3. **Резюме** — `hhru list-resumes` (в конфиге должен быть реальный
   `resume_url`, а не плейсхолдер).

## Запуск Chromium из Codex

Любую команду, которая открывает Chromium, запускай из Codex **с первого раза** с
`sandbox_permissions=require_escalated`. Не делай пробный запуск в sandbox:
на macOS он заведомо упирается в Crashpad/Mach-port permissions, а для
WRITE-workflow создаёт лишний риск вокруг durable-аудита. Это правило одинаково
для headed и `--headless` режимов.

Всегда требуют Chromium: `login`, `login-code`, `search`, `apply`, `bump`,
`run`, `probe`, `responses`, `refresh-token`, `call-api`, `fill-form`, команды
создания, копирования, переименования, публикации, удаления и браузерного
редактирования резюме. `clear-negotiations` требует его только для
`--account-wide` или боевого `--topic`; фильтры `--vacancy`/`--resume` и
`--topic --dry-run` являются plan-only. Условно требуют Chromium:
`list-resumes` без `--local` и `whoami --online`. Обычный `whoami`,
`list-resumes --local`, `stats`, `query`, `funnel`, `market` и другие локальные
команды можно выполнять в sandbox.

Elevated-разрешение разрешает только технический запуск процесса и **не является
подтверждением WRITE-действия на hh.ru**. Для внешних изменений по-прежнему
обязательны dry-run, показ плана и отдельное явное подтверждение пользователя.

Если браузерную команду всё же запустили в sandbox, CLI завершится до браузера,
write-lock и durable run с маркером `CODEX_SANDBOX_BROWSER_REQUIRED`; повтори
ровно ту же команду с `sandbox_permissions=require_escalated`. Старый маркер
`CODEX_SANDBOX_BROWSER_FAILURE` остаётся резервной диагностикой для среды, где
preflight не смог распознать ограничение. Не переустанавливай Chromium и не
считай это ошибкой hh.ru или сохранённой сессии.

## Длительные команды: только наблюдаемый foreground

`competitors collect` всегда запускай с явными параметрами режима и прогресса:

```bash
hhru --headless competitors collect --text "AI" --max-pages 5 \
  --auth-mode anonymous --detail-workers 10 \
  --execution-mode foreground --progress-verbosity 1
```
По умолчанию `competitors collect` использует `--auth-mode anonymous`: создаёт
чистый browser context без `storage_state` и cookie аккаунта. Авторизованный
режим включается только явно через `--auth-mode authenticated`.
`--detail-workers` принимает 1–1000 и по умолчанию равен 10. Не запускай
несколько отдельных команд: параллелизм принадлежит одному foreground run,
который сохраняет общий checkpoint. Для authenticated используй 1 worker.
Skills и собранный свободный текст сохраняются без privacy-фильтра; не называй
отброшенную анкету штатным privacy-исходом.
Эту и другие команды, работающие дольше одного tool-вызова,
нельзя запускать через `&`, `nohup`, `run_in_background` или иной detached-режим.
Запусти команду в foreground terminal session. Если terminal tool вернул session
ID, сохрани его и продолжай читать новые чанки не реже одного раза в 60 секунд,
пока команда не вернёт exit code. Не завершай свою задачу и не говори, что процесс
«продолжается», если больше не наблюдаешь эту terminal session.

Пользователь должен получить:

1. Сразу после `[ESTIMATE]` — оценку времени и её основание. Для повторного объёма
   можно дополнительно экстраполировать фактическое время предыдущей страницы.
2. После каждого `[HEARTBEAT]` или `[PROGRESS]` — короткое обновление: сколько
   прошло времени, текущая страница, обработано/сохранено, ошибки и актуальный ETA.
3. При отсутствии строки дольше 60 секунд — проверку terminal session и durable
   checkpoint в SQLite; молчание нельзя трактовать как продолжающуюся работу.
4. Только после завершения — exit code и финальную строку `[STOP]` либо
   `Конкуренты: ...`. Если session исчезла, прочитай run по `run_id` из SQLite и
   прямо сообщи, что живое наблюдение потеряно; не называй такой run активным.

Если пользователь просит остановить процесс, отправь SIGINT в ту же terminal
session, дождись `[STOP]` и сообщи последний checkpoint. Не оставляй процесс в фоне.

Для короткой живой проверки полного lifecycle используй
`--items-per-page 20 --max-pages 1`; production-дефолт остаётся 100 карточек на страницу. Не ускоряй
smoke-test отключением или уменьшением троттлинга.

После успешного smoke сообщи пользователю измеренное время и оценку реального
запуска до его старта: `smoke_elapsed / smoke_processed * requested_details`.
Покажи центральное значение и диапазон ±25%, назови объём smoke и целевой объём.
Например, 20 деталей за 6 минут дают для 100 деталей около 30 минут (23–38).

## Справочник команд

| Команда | Природа | Что делает |
|---|---|---|
| `login` / `login-code` / `import-cookies` | WRITE-local | вход, сохранение сессии |
| `search` | READ | поиск вакансий по фильтрам (без откликов) |
| `apply` | WRITE-hh-ru | отклик с письмом (dry-run-first) |
| `bump` | WRITE-hh-ru | поднятие резюме (кулдаун 4ч) |
| `run` | WRITE-hh-ru | полный цикл apply + bump |
| `probe` | READ | дамп формы отклика без отправки |
| `stats` / `query` | READ | сводка / read-only SELECT к истории |
| `responses` / `funnel` | READ | ответы работодателей / воронка |
| `whoami` / `list-resumes` | READ | сессия и резюме |
| `market` | READ | агрегаты рынка |
| `update` | WRITE-local | единое обновление CLI и Codex plugin с проверкой commit |
| `mark` / `clear-skipped` | WRITE-local | пометка оффера / очистка skipped |
| `select-photo` | WRITE-hh-ru | назначить резюме УЖЕ ЗАГРУЖЕННОЕ фото из библиотеки аккаунта (галерея «Все загруженные фото»): `--dry-run` печатает инвентарь с photo-id, боевой запуск требует `--photo-id <id>` + `--force` |
| `upload-photo` | WRITE-hh-ru | загрузить НОВЫЙ файл (jpg/png) в резюме через file-input; замена существующего фото не поддерживается |
| `delete-photo` | WRITE-hh-ru | скрыть фото из резюме или удалить из библиотеки hh.ru |
| `publish-resume` / `reply-employers` / `clear-negotiations` / `copy-resume` | WRITE-hh-ru | деструктивные/массовые, требуют `--force` или подтверждения |

## Типовые задачи

- **Добавить фото на резюме.** Если фото уже загружено в библиотеку аккаунта
  (галерея «Все загруженные фото» во вьюере на странице резюме) — это
  `select-photo`, а НЕ `upload-photo`: `select-photo --resume <id> --dry-run`
  печатает инвентарь библиотеки с числовыми photo-id, затем
  `select-photo --resume <id> --photo-id <id> --force`. Инвентарь отдаёт только
  id без содержимого — не скачивай файлы для «визуальной сверки»; какую
  фотографию брать, уточни у пользователя по id/порядку (порядок инвентаря до
  сих пор совпадал с порядком галереи во вьюере, но это наблюдение, не
  гарантия). `upload-photo` — только для нового файла с диска.

- **Найти вакансии** — `search --resume <id> --dry-run --max-pages N`.
- **Откликнуться** — см. скилл `hhru-apply`.
- **Анализ рынка** — см. скилл `hhru-market`.
- **Мониторинг/статус** — см. скилл `hhru-monitor`.

Если задача не покрыта скиллами — используй справочник команд выше и правила
безопасности. Не выдумывай флаги, которых нет в CLI: при сомнении покажи
`hhru --help`.
