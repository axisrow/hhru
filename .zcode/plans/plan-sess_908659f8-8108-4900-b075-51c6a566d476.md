# План: issue #142 — задействовать ready_selector, свести таймауты и обходы goto_hh

## Контекст

`goto_hh(page, url, *, ready_selector=None)` (browser.py:31) поддерживает параметр `ready_selector`, но **0 из 9 callers** его передают — мёртвый параметр. Каждый модуль ждёт готовность страницы по-своему. Плюс `commands/probe.py:143` обходит `goto_hh` (сырой `page.goto` без retry), а `probe.py:306` имеет хардкод `60000` вместо `GOTO_TIMEOUT_MS`.

Решения по неоднозначным пунктам (пользователь не ответил — выбрал наиболее обоснованные):
- **probe retry**: обернуть `goto_hh` в try/except → `unreachable` (даёт retry, сохраняет семантику #120)
- **таймауты**: минимально — убрать только голый хардкод `60000`, специализированные оставить с комментариями (соответствует формулировке issue)
- **scope**: всё за один заход, с резервным разрезом если выйдет >1000 LOC

## Часть 1. `ready_selector` в точках вызова `goto_hh`

### 1a. `copy_resume.py:62` и `:138` — список резюме
- Передать `ready_selector=RESUME_LIST_CARD` (`[data-qa='resume']`) в оба вызова `goto_hh(page, RESUMES_LIST_URL)`.
- `RESUME_LIST_CARD` уже импортирован (строка 29). Это отмечает готовность списка — карточка резюме отрендерена.
- **Нюанс:** после этого `card_locator.wait_for(timeout=COPY_TIMEOUT_MS)` на строках 74-80 остаётся — он ждёт *конкретную* карточку по `resume_id`, а `ready_selector` только *любую*. Они не дублируют друг друга. Оставить с коротким комментарием.

### 1b. `responses.py:258` — НЕ трогать (специфическое ожидание)
- Ручной `wait_for(state="attached")` на строках 277-287 намеренно отличается от `ready_selector`:
  - `state="attached"` (не visible), `RENDER_TIMEOUT_MS=10_000` (не 90_000), ловит `PlaywrightError` с warning и трактует как empty inbox (не рейз).
  - Семантика: «отличить грузящуюся страницу от genuine-empty».
- **Добавить комментарий** (~3 строки) перед блоком 277: «почему не ready_selector в goto_hh выше — нужен attached+короткий таймаут+warning, а не visible+90с+raise».

### 1c. Остальные 7 callers — НЕ трогать
- `auth.py:49`, `browser.py:126` (is_logged_in), `bump.py:32`, `search.py:225`, `apply/pipeline.py:103`, `apply/probe.py:144` — после них либо нет специфического ожидания готовности, либо оно делается через `expect_navigation`/`wait_apply_button` (apply-путь, своя навигация).
- В issue сказано: «Где ожидание специфичное — оставить, но зафиксировать в комментарии почему». Для apply/steps.py `expect_navigation` — это не вызов `goto_hh`, а параллельный путь навигации; трогать его в этой задаче не нужно (он обоснован в #80).

## Часть 2. `commands/probe.py` — перевести на `goto_hh`

### 2a. `check_selectors` (строка 143) → `goto_hh` с retry + unreachable
- Заменить `page.goto(url, wait_until="domcontentloaded")` на `goto_hh(page, url)`.
- Импортировать `goto_hh` из `..browser` (вверху файла или локально в функции, как уже сделано для `launch_context`).
- Обернуть вызов в `try/except (PlaywrightTimeoutError, PlaywrightError)` → `PageCheck(unreachable=True)` (сохранить логику #120). Теперь probe получает retry (до 3 попыток внутри goto_hh), но при провале всех попыток — `unreachable`.
- **Важно:** `except Exception` сузить до `(PlaywrightTimeoutError, PlaywrightError)` — это то, что рейзит goto_hh; более узкий catch соответствует «не прятать баги».

### 2b. `run_healthcheck` (строка 306) — убрать хардкод `60000`
- Удалить `page.set_default_navigation_timeout(60000)`.
- `launch_context` уже выставляет `set_default_navigation_timeout(GOTO_TIMEOUT_MS=90_000)` (browser.py:110). Строка 306 дублирует это с *меньшим* значением (60с < 90с), что противоречит — сейчас probe ходит с 60с, остальной код с 90с.
- Удаление делает probe единым с остальным проектом (90с). Обновить комментарий.

### 2c. Регрессионный тест «непрогрузившаяся страница → UNREACHABLE, не NOT_FOUND»
- В `tests/test_probe_healthcheck.py` добавить тест: `goto_hh` monkeypatch'нут на raiser `PlaywrightTimeoutError` → `check_selectors` возвращает `PageCheck(unreachable=True)`, `format_healthcheck_table` рисует `STATUS_UNREACHABLE`, итог `[FAIL] ... недоступно страниц: 1`.
- Сейчас `_FakePage.goto` (строка 36) поднимает `Exception` для unreachable-сценария — нужно либо оставить и убедиться что goto_hh пробрасывает, либо monkeypatch'нуть `goto_hh` в модуле `probe`.

## Часть 3. Хелпер `count → wait_for → count` в `copy_resume.py`

### 3a. Вынести идиому в функцию
- Идиома повторена дважды (строки 72-87 для `card_locator`, 104-122 для `duplicate_locator`). Вынести в приватный хелпер, например:
  ```python
  def _wait_single_match(locator, *, timeout_ms: int, missing_reason: str, ambiguous_reason: str) -> ... | None:
      """count→wait_for→count с fail-closed семантикой.
      
      Возвращает locator.first при ровно 1 совпадении, либо None (с reason в Return).
      """
  ```
- Точная сигнатура — продумать при имплементации: идиома возвращает `CopyResumeResult` при провале, поэтому хелпер может принимать колбэк-фабрику reason или возвращать кортеж `(count, ...)`. Предпочту вариант, возвращающий `int` (итоговый count) + документирующий контракт «count==1 → ок», а reason-форматирование оставить на callsite (меньше связности).

### 3b. Использовать хелпер в обеих точках
- Заменить блоки 72-87 и 104-122 на вызовы хелпера.
- Сохранить все комментарии про strict-mode violation и fail-closed (перенести в docstring хелпера).

### 3c. Симметрия `_card_hashes` после goto (строка 138-139)
- После `goto_hh(page, RESUMES_LIST_URL, ready_selector=RESUME_LIST_CARD)` на строке 138 — теперь готовность обеспечивается `ready_selector`, асимметрия с строкой 62 устранена (там тоже добавлен `ready_selector`).
- `_card_hashes` на строке 139 работает на готовом DOM — комментариев достаточно.
